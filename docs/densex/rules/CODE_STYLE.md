# 程式風格

寫程式或審查程式時適用。基本規則在根目錄的 `AGENTS.md`。

## 一般原則

- 融入周圍的程式碼。
  - 重用既有的基礎設施；它妨礙 DenseX 的需求時，就直接替換掉。
  - 不要新增功能重複的平行子系統。

## 註解（擁有者 2026-11-18 決定）

- **共同原則**：
  - 簡短（1～2 行），只在需要的地方寫，說明「為什麼」。
  - DenseX 自己的改動，註解開頭標 `DenseX`。
- **一般情況**：新寫的註解用正體中文。適用於 `src/`、`common/`、`tools/`、`tests/` 的 C/C++，以及 Python、PowerShell、CMake。中文註解可以用全形標點。
- **例外**：`ggml/` 整個目錄（含 CUDA 的 `.cu`／`.cuh`）的註解，維持簡單英文，而且只用 ASCII。
  - 理由：`.cu` 檔由 nvcc 交給 MSVC 編譯，這條路徑沒有設定 `/utf-8`。中文可能被當成 cp950 誤解碼，最壞的情況是吃掉下一行程式碼，而且編譯不會報錯。
  - `ggml/` 裡的標頭會被 `.cu` include，所以整個目錄一起列為例外。
- **既有的英文註解**：不需要整批翻譯。修改到某段註解時，可以順便改寫成中文（`ggml/` 除外）。
- 註解不要為了配合欄寬硬換行，也不要把一句話拆成好幾行。

## 程式結構（擁有者 2026-11-18 決定）

目的：讓 agent 和人類開發者都看得懂程式碼；出問題時，容易找到根源。

### 優先順序
- 精度和穩定度是不能跨的門檻：regress 必須通過，輸出逐字相同，工具調用 14/14。
- 性能是在門檻內盡量追求的目標。
- 「快一點但精度掉一點」的改動，不能用預設開啟的方式進來，見 `AGENTS.md` 基本規則 2。

### 看得懂
- 每個 DenseX 功能自成一塊：有自己的檔案和開關。
- 新功能的檔案開頭用幾行說明：
  - 做什麼；
  - 輸入與輸出；
  - 開關與預設值；
  - 依賴哪些模組。

### 解耦
- 模組之間只透過明確的函式介面溝通，不直接讀寫對方的內部狀態或全域變數。
- 每個功能都能單獨關掉，關掉後的舊路徑就是對照組。出問題時，關掉某個功能就能判斷是不是它造成的。
- 修改既有的上游程式碼時，只要求不讓耦合變更嚴重，不連帶重構整個檔案。真的需要解耦，另外開 issue。
- 不為假想的未來需求加抽象層、registry 或擴充點；模組的邊界依實際功能劃分。
- 熱路徑例外：CUDA kernel、合併運算這類熱路徑，可以為了速度犧牲易讀性或解耦。條件是：
  - 有實測的效能收益；
  - 寫註解說明原因與收益。

### 錯誤看得到（不准默默失敗）
- 在邊界驗證：載入模型、讀設定、接收請求。kernel 內部不做逐元素檢查。
- 錯誤訊息開頭標出模組名稱，例如 `dflash: ...`，一看就知道是哪一塊出問題。
  - 新程式碼一律要標。
  - 既有的錯誤訊息，修改到那一則時順便補上。
- 刻意設計的退路可以保留，例如 VRAM 不夠時改用 CPU，但一定要印出警告。
- 會改變數值結果的退路，不准默默發生：必須直接報錯，或明確提示使用者。
- 不吞例外，不把錯誤換成預設值繼續跑。

## 程式碼本身

- 程式碼只用 ASCII，包括識別名稱、字串常數和 log 訊息：用 `-`、`->`、`x`、`...`，不用破折號、箭頭、乘號或刪節號。
- 命名沿用 llama.cpp 的慣例：
  - 函式用 `snake_case`，命名採「最長共同前綴」；
  - C/C++ 檔名用 `kebab-case`；
  - enum 值全大寫，並以 enum 名稱為前綴。
- llama.cpp 在 `common/jinja` 有自己的 Jinja 引擎，不是 Minja。這個 codebase 裡任何提到 Minja 的地方都是錯的。
